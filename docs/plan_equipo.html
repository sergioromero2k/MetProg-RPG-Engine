Interfaz gráfica: GUI o consola

El enunciado dice literalmente: "mostrando un menú por consola o con una GUI, como el alumno quiera". La recomendación es:

Usar consola (Scanner + System.out). Es lo más rápido, lo más seguro y lo que más se evalúa en esta asignatura. No perdáis tiempo haciendo una GUI bonita si el código por detrás no está completo. Si acabáis pronto podéis añadir una GUI simple con JavaFX, pero no es necesario.
No usar Swing. Está obsoleto. Si queréis GUI usad JavaFX, pero insisto: primero la consola al 100%.

Cómo evitar que os bloqueéis

Regla de oro: nadie espera a nadie

P2 primero →Las clases del modelo no dependen de nada. P2 empieza el día 1 sin necesitar a nadie.
P3 en paralelo →Los menús pueden hacerse con clases vacías (stubs). P3 escribe los menús y cuando P2 acabe las clases reales las conecta.
P1 en paralelo →Los patrones y el motor de combate se programan sobre las clases abstractas. No necesita que P2 acabe todo, solo que cree las clases base.
GitHub branches →Cada uno trabaja en su rama. Nadie rompe el código del otro. Al final del día se hace merge a main.

Cómo usar GitHub sin chocaros
🌿

Una rama por persona

P1 trabaja en rama-p1, P2 en rama-p2, P3 en rama-p3. Nadie toca la rama main directamente.

🔀

Merge cada noche

Al final del día P1 hace el merge de las tres ramas a main. Es el jefe técnico, resuelve los conflictos.

📦

Stubs para no esperar

Si necesitas una clase que aún no existe, créala vacía con métodos que devuelven null. Luego P2 la rellena.

💬

Commits con mensaje

Cada commit con mensaje claro: "Añade clase Vampiro", "Implementa patrón State". Nada de "fix" o "cambios".

🎓

Profesor colaborador

Añadir al profesor como colaborador del repositorio desde el primer día. Es obligatorio según el enunciado.

⚠️

Estudiad todo el código

En la defensa el profesor os pregunta individualmente. Cada uno debe entender el código de los otros dos.
